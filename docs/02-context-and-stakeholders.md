# 02 — Context and Stakeholders

## Stakeholder analysis

| Stakeholder | Need / expectation | ISMS relevance |
|---|---|---|
| Executive Management | Regulatory assurance and risk oversight | Approves scope/policy and accepts residual risk |
| Information Security & Compliance | Clear mandate and executive backing | Owns and operates the ISMS; leads audits |
| IT Operations | Security integrated into infrastructure | Implements technical controls and manages cloud/network |
| SED / DevOps | Security embedded into development | Secure coding, CI/CD controls and vulnerability scanning |
| Acquiring Banks & Card Schemes | Evidence of PCI DSS compliance | External compliance and audit expectations |
| Merchants | Confidence that payment data is protected | Contractual security expectations |
| Regulators | Demonstrable legal and regulatory compliance | Oversight and enforcement |
| Third-party facility contractors | Clear written security obligations | Physical security and contractual controls |

## Information security policy themes

The source policy commits to:

- Confidentiality, integrity and availability
- Legal, regulatory and contractual compliance
- Measurable information security objectives
- Adequate people, technology and budget
- Staff security responsibilities
- Continual improvement through PDCA
- Need-to-know and least-privilege access
- Security by design
- Prompt incident reporting
- Supplier accountability

## Data classification

| Classification | Examples |
|---|---|
| Restricted | Cardholder PAN/CVV, cryptographic keys |
| Confidential | Merchant settlement data, source code, HR records |
| Internal | SOPs, internal reports, project data |
| Public | Marketing material, public API documentation |

## Evidence principle

The repository should demonstrate the reasoning behind controls rather than merely listing controls. Each important risk should be traceable to treatment, control, implementation evidence and review.
